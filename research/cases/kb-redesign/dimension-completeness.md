# 维度完整性：方法与约束（设计，待审）

> 梳理一个知识领域时,先对标建立完整的维度框架,再在完整框架上按 80/20 取舍,写出快速上手。本文说明这条方法,以及怎么约束它——事前用 agent 规则、事后用机器校验,人只审内容对错。

## 方法

学一个领域,常见的问题是只深化已经会的部分,漏掉自己没意识到的维度。对策是先建这个领域的完整维度框架(没内容的维度先留空、标出来),再往里填。

这条方法在几个层面都用过:主题树做过五路外部对标,内容类型做过 Diátaxis / Good Docs 两路对标。放到单个领域内部,就是学某个技术栈时先建完整维度、再深入。它是一条通用做法,不是新的内容类型,也不改动四维度框架。

## 三步

1. 先建完整维度框架。
2. 在完整框架上按 80/20 取舍,找出能解锁大部分使用的少数维度。
3. 这少数维度写成快速上手,完整框架本身保留为领域全景。

第 2 步必须在完整框架上做。否则取舍的对象只是你已经会的部分,漏掉的维度仍然没进视野。先有完整框架,80/20 的取舍才可靠。

## 两个产物

- 领域全景:完整维度框架加盲区标注。对应 tech-landscape 题材(explanation / concept)。
- 快速上手:框架上按 80/20 选出的入门路径。对应 quickstart 题材(tutorial / task)。

两者配套。只有全景没有快速上手,读者面对全图无从下手;只有快速上手没有全景,读者会把入门路径误当成领域全部。两个都不是新类型,方法给它们补的是写法,不是往框架里加东西。每个领域必须有全景(建领域第一步就得有,哪怕先是满是盲区的维度清单);quickstart 按需,不强制每个领域都写。

## 三层约束

- agent 规则(事前):约束 AI 按什么流程写。
- 机器校验(事后):检查形式条件是否达标。
- 人审(最后):判断维度是否齐全、80/20 取舍是否准确。

| 环节 | agent 规则 | 机器校验 |
|---|---|---|
| 建维度框架 | 先对标外部权威结构列维度,不凭记忆;登记进 subjectScheme | 领域 map 必须挂一个全景 topic;全景必须有对标来源 |
| 盲区 | 没内容的维度留空并标出,不跳过 | 覆盖度可算,盲区是词表有、无对应 topic 的差集,构建时自动列出 |
| 快速上手 | 按解锁度/使用频率取舍,不按熟悉度;xref 到全景,声明覆盖哪些维度、略过哪些 | quickstart 必须 xref 到所属全景并有取舍声明,否则报错 |
| 维度是否齐全、取舍是否准 | 约束用对方法(先对标、按频率) | 机器判断不了,交人审 / AI 交叉验证 |

维度是否齐全、80/20 取舍是否准确,机器判断不了,原本只能靠人审。agent 规则介于两者之间:它不能保证结果对,但能要求方法对——要求先对标再列维度、按使用频率而非熟悉度取舍。机器检查是否做到,规则约束方法,人审判断对错。

## 维度怎么落进词表和全景

subjectScheme 现有结构是"领域 > 技术"(web > react/nextjs),子节点是具体技术,不是维度。所以维度不能直接当子主题塞进去,分两处放:

- subjectScheme 加一个横切的维度值集(和 maturity/volatility 一样是横切受控值),登记一套受控的维度名。
- 每个领域全景 topic 用这个值集,声明本领域的完整维度清单。全景本来就是完整维度框架,维度清单落在它身上最自然。
- 每篇 topic 标自己覆盖哪个维度。

标引机制(查 DITA 2.0 规范后定):DITA 2.0 移除了 classification domain,受控维度标引用专门化属性 `@dimension`(从 `@props` 专门化、`enumerationdef` 绑受控值,照 maturity 模式加的第四个属性域)——内容 topic 根标 `dimension="dim-…"`(可多值);全景的规划清单与域用 prolog `data`(`planned-dimension`/`domain`,属治理元数据)。

这样覆盖度可算:全景声明的维度里,有多少有对应 topic 覆盖,构建期按 domain 分组求差算得出;盲区是全景声明了、但没有 topic 覆盖的维度,构建期可列。复用现有构件(subjectScheme、属性域机制、构建报告)+ 新增第四个属性域 `dimensionAttDomain.rng`。已在 `kb/topics/web/electron-landscape.dita` 样板跑通 `dita validate`。

这和三步自洽:第 1 步"建完整维度框架"的产物,就是在全景里列出维度清单、并往 subjectScheme 登记新维度值。建框架和填词表是一个动作。

## 机器管不到的部分

词表里维度列得全不全、快速上手的 80/20 选得准不准,机器判断不了,交人审或 AI 交叉验证。机器只保证形式条件:有维度框架、有对标依据、盲区列出、快速上手挂靠全景、题材结构完整。

## 落地（并入第一批工具链）

1. Schematron 新增两条规则(接在来源规则 R8 后):
   - R9:领域 map 必须挂一个领域全景 topic(tech-landscape)。
   - R10:quickstart 必须 xref 到所属全景并有取舍声明。
   （原设想的"全景必有对标来源"不单列——全景是 concept,已被来源规则 R8 覆盖。）
2. subjectScheme 加维度值集 + 全景声明维度清单:现有子节点是技术不是维度,所以维度做一个横切值集(与 maturity/volatility 同类);每个领域全景 topic 用它声明本领域完整维度清单;topic 用 @subjectrefs 标覆盖的维度;构建报告算覆盖度、列盲区。落在 kb/vocab/subjectScheme.ditamap 和各领域全景 topic。
3. agent-rules 新增一条写作规则 topic《维度完整性写作规则》:先对标列维度不凭记忆、盲区标出、80/20 按解锁度、quickstart 挂靠全景。并入 kb/topics/engineering/agent-rules-core.dita 和 kb/maps/deliverables/agent-rules.ditamap,单源输出成各工具的规则文件。

## R9 的粒度落定与反向检测（2026-08-20 补）

上面的落地一节写的是"领域 map 必须挂全景",粒度指向九个分支 map。实做时粒度已经走到更细的一层,这里把决定写下来,不再让它只存在于代码里:

1. **R9 的"领域"= 技术域(topic prolog 里 `data name="domain"` 的键),不是九分支的领域 map。** 依据:全景是按域立的(dita / electron / coding-agents / writing-principles 各一篇),一个分支下可以有多个域(知识工程分支同时有 dita 与 writing-principles);覆盖度、盲区、对标登记(`bm-*`)也全部按域记。分支 map 层面不设硬性要求——分支是编排容器,`ia` 的分支统计里保留"· 无全景"作为观察。
2. **豁免按分类法滚算,与正向覆盖表对称**:子键挂在有全景的祖先下即算有主(claude-code 的 topic 归 coding-agents 的全景管),不要求每个叶子键都立一篇近乎相同的全景。不声明 `domain` 的 topic(术语库)不参与。
3. **检测有两面,缺一即有静默通过**。正向:覆盖表按域算覆盖度与盲区——但它只为已有全景的域建条目,域缺全景时连一行都不出。反向(2026-08-20 补进 `dita-tools ia`):有内容却无全景的域,在"需要处理"里点名,不受 `--details` 门控。触发事由:知识工程分支一度被嵌套 map 里的 dita 全景遮住,writing-principles 十余篇内容无全景而工具零输出;全景补上后,coding-practices(1 篇)仍处在同样的静默里,直到反向报表落地才现形。
