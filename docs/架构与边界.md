# 架构与边界

> 三层各自做什么、不做什么，以及规则归谁实现。写于 2026-08-15，起因是 `kb` 与 `dita-tools` 各自演进出现割裂。
>
> **本轮只画边界，不定工具终态**——规则归属表里标"待定"的项，是真的还没决定，不是忘了填。

## 一、为什么需要这份文档

三块本来在不同仓库，合并后没人定过它们的关系，于是出现四个接缝：

1. **没有根。** 仓库根目录只有三个文件夹，没有入口文档。三份 README 各说各的，只有 `dita-tools/README.md` 提了一句"作为 kb 的配套工具链"。（已补：根 [README.md](../README.md)）
2. **同一条规则被两份规划各自认领。** `docs/IA治理.md` 说 R11 加进 `check-rules.xsl`；`dita-tools` 的架构计划说 R11 进 `dita_validate`。两边都动，就会长出两个都不完整、还得互相同步的实现。
3. **唯一事实源没被当成唯一事实源。** `vocab/subjectScheme.ditamap` 定义了 51 个 `dim-*` 与三个属性值集，但 `check-rules.xsl` 里是**手抄的副本**。改词表不会让校验跟着变。
4. **工具够不着内容。** `dita-tools` 有 map 解析器，没有 topic 解析器；`TopicMeta` 类型定义了却没有生产者。它因此读不到任何 `@props` 专门化属性，接不上覆盖度与业务规则。

## 二、三层契约

```
docs/        研究与设计   产出：判据、规则规格、裁定记录
  │                        不做：不实现、不校验
  ↓ 规格（R1–R11 的定义与理由）
kb/          内容正本     产出：内容 topic、受控词表（唯一事实源）、交付物
  │                        不做：不定义规则的"为什么"（那在 docs）
  ↓ 值集与内容（subjectScheme + topics/ + maps/）
dita-tools/  执行引擎     产出：校验结果、IA 视图
                           不做：不自带值集、不重新定义规则语义
```

**依赖单向，反向即违规。** 三条具体的红线：

- 工具**不得**内联合法值清单——一律从 `subjectScheme.ditamap` 读。当前 `check-rules.xsl` 的硬编码副本是违规的历史欠账，谁接手 R11 谁一并还。
- 规则的理由写在 `docs/`，实现里只留一行指向规格的引用。工具的 README 不承载"为什么这么定"。
- `kb` 不依赖 `dita-tools` 才能用。工具缺席时，`dita validate` + 现有脚本仍能跑完整条链——工具是加速器，不是必需品。这条保证工具可以慢慢换，内容不被绑架。

## 五、参照实现只能借机制，不能借需求

2026-08-15 的实例，值得当成一条纪律记着。

`dita-tools` 的架构计划里，立项的头号理由是「看不到……**哪些域是空的**」，而三百行之后的实现规格写的是「XML → AST（**递归展开 mapref**）」，参照 DITA-OT 的 `MaprefModule.java`。展开即内联，**空 map 会连同标题一起消失**——这份计划的实现规格，恰好取消了它自己的头号需求。代码忠实执行了规格，测试也照着规格写（`expands_mapref_inline` 直接给缺陷背书），于是测试全绿、缺陷存活，直到工具第一次真跑在 kb 上才暴露。

DITA-OT 那样做没有错：它要产出页面，空 map 本就没有页面可产。**错在借的时候只问了"它怎么做"，没问"它为什么这么做、我的目的和它一样吗"。**

由此定三条：

- 参照实现给的是**机制**。机制背后的目的必须重新对照本项目的立项理由，不一致就不能照抄。
- 每条实现规格要能指回它服务的哪条需求；指不回去的规格，要么是多余的，要么是抄来的。
- **测试照规格写，所以测试兜不住规格本身的错。** 规格与需求的一致性只能靠人对照，或者靠让工具尽早跑在真实数据上——这也是"工具先行、小步验证"的实际理由。

## 六、文档纪律

- `docs/cases/` 下的评审单、阶段总结、Phase 结论是**历史记录**：按当时原样保留，不翻新路径、不追改结论。要更正就新写一篇并注明取代关系。
- 现行文档（各级 README、设计正本、进行中的计划）**必须与现实一致**，发现不符即改。
- 判断与事实分档写：来源节区分「已核对」与「判断与通用实践」，见 `kb/topics/writing/writing-sourcing.dita`。

## 八、执行顺序（已定）

**工具先行**：先把治理链打通，再批量扩内容。理由是现在只有 22 篇，规则和标注方式都还改得动；等写到两百篇再改工具，返工成本按篇数放大。

**工具这一侧，当前主线是 IA 视角**（2026-08-15 定），不是预处理引擎。IA 视角有两个用途，前者是现在的迫切需求：

1. **建库之初的全局观测与设计** —— 知识树长什么样、哪些域是空的、哪些域缺哪一类内容、哪些还是 draft、哪些维度没覆盖。这是决定"下一批写什么"的依据。
2. **面向使用者 / 作者视角的页面渲染**（未来）—— 从"结构观测"走向"内容可读"。

**`topic` 解析器因此归位为 IA 视角的前置，不是与之并列的另一条赛道**：上面第 1 条里除"知识树"和"空领域"外的每一项，都要求读到 topic 的 `@dimension` / `@maturity` / `@volatility` 与类型。R11 是它到位后的顺带产物。Key Space / Conref 等预处理大件顺延。

前置条件已解除：`build-essential` 已装，`dita-tools` 于 2026-08-15 首次编译通过、测试全过。
