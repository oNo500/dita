# 12 · DITA 的哲学与原理

> 这一篇不讲怎么用，讲**为什么它必须长成这样**。
>
> 方法是从一条公理出发往下推。凡是能被推导出来的，就不是"设计选择"，而是**约束的必然结果** —— 理解了这一点，DITA 的大部分怪异之处会从"要背的规则"变成"想想就知道"。

---

## 一、公理

> **同一个事实，应当只存在于一个地方。**

就这一条。DITA 的全部机制都是把它贯彻到散文（prose）上的结果。

### 为什么这是个真问题

技术文档本质上是一个映射：

```
(产品, 受众, 语境, 渠道) → 文本
```

朴素做法是给每个组合写一份文档。代价是 `N_产品 × N_受众 × N_渠道` 份内容，每份独立维护。

问题不在**存储**冗余，而在**变更**代价。一个事实变了，你要：

1. 找出所有包含它的文档 —— **而这个信息没有任何地方记录**
2. 逐一修改
3. 保证没漏

第 1 步是关键。副本之间**没有身份关联**，"这两段说的是同一件事"这个知识只存在于人的记忆里。于是一致性依赖记忆，而记忆会失效。

这就是数据库里的**范式化（normalization）**问题。同一个事实存多份、无主键关联，导致更新异常。

**DITA 是把范式化应用到散文上。**

一旦接受这个类比，后面全是推论。

---

## 二、推导

### 推论 1：复用要求可寻址，可寻址要求有身份

若一个事实只存在一处，则其余位置必须**引用**它。引用需要**地址**。地址需要**标识**。

→ `@id`、`@conref`

这一步没有选择余地。

### 推论 2：复用单元的粒度是被"正确性"决定的，不是被"方便"决定的

粒度选多大？

- **太细**（按句）：寻址开销超过内容本身；更重要的是**片段脱离语境后往往是错的**
- **太粗**（按文档）：想复用的部分没法单独取出

所以必然存在一个中间单元。它的边界由什么决定？

> **能被独立理解的最小内容块。**

一段内容如果放到新语境里还成立，说明它自带了理解所需的全部条件。这样的块才能安全复用。

→ **topic**

**关键认识：topic 不是一个任意的分块惯例，它是"被复用的内容必须在新语境里仍然正确"这个要求逼出来的。** 粒度大小是次要的，**自足性**才是定义。

### 推论 3：可复用性要求"禁止"，而不只是"允许"

若一块内容可能出现在任何位置，它就**不能假设自己在哪**。于是必须禁止：

- "如上所述"、"下一章将讲到"
- 依赖章节编号的表述
- 写死的产品名（不同变体不同）

**这是一种负能力（negative capability）。** DITA 的价值有相当一部分来自它**不让你做什么**，而不是让你做什么。

这解释了一个常见困惑："Markdown 也能写文档，为什么要 DITA？"——因为 Markdown **允许**你写"如上所述"，而允许即是纵容。格式的约束力就是它的价值。

### 推论 4：顺序和层级必须外置

既然 topic 不能知道自己在哪，那"在哪"这个信息必须存在别处。

→ **map**

map / topic 的分离不是模块化的美学偏好，是推论 3 的直接后果。

**推论 4 的推论**：topic 之间的交叉引用也不能写死目标位置 —— 因为目标在哪取决于当前是哪个 map。所以引用必须**间接**。

→ **keyref**

**keyref 不是一个便利特性。它和 topic 是同一个约束逼出来的。** 这解释了为什么 DITA 老手会说"能用 keyref 就别用 href"——那不是风格偏好，是架构一致性。

### 推论 5：变体处理必须是正交维度，不能是层级

同样的内容要出多个变体。两条路：

- **(a) 复制后修改** —— 回到了公理要消灭的问题
- **(b) 单一来源 + 标记 + 构建时过滤**

只能选 (b)。那么标记的形态呢？

变体的维度是**正交**的：平台 × 受众 × 产品 × 交付渠道。若用目录或分支来表达，`N` 个维度各 `M` 个取值需要 `M^N` 个分支，组合爆炸。

正交维度只能用**正交的标记**来表达 —— 即多个独立属性。

→ `@platform` `@audience` `@product` `@deliveryTarget`，以及可专门化的 `@props`

这也解释了为什么 DITA 的条件化不是 C 语言式的 `#ifdef`：`#ifdef` 是一维的（要么定义要么没定义），表达不了正交组合。

### 推论 6：类型化的双重理由

为什么要 concept / task / reference？两条独立的理由，强度不同。

**理由一（工程性的，很硬）：一致的结构才可被程序处理。**

若所有 task 形状一致，你就能统一地生成、校验、转换、索引它们。若每篇形状随意，任何自动化都得先做一遍猜测。**结构的可预测性是自动化的前提。**

**理由二（认知性的，较软）：类型化是对作者的强制函数。**

主张是：概念和步骤混在一段里，是内容不可复用的根源。让作者**动笔前先声明类型**，可以在源头阻止这种混合。

诚实地说：**理由一是站得住的，理由二证据薄弱。** 具体的三分法（concept/task/reference）带有 Information Mapping 的历史印记，它是一个**选择**，不是推导结果。你完全可以设想一套不同的类型集合而不损害 DITA 的其余部分。

**但"要有类型"本身是推导出来的**（理由一），只是**"是这三种"不是**。区分这两层，能避免把可争论的部分当成不可动摇的教条。

### 推论 7：扩展机制 —— 这是 DITA 唯一真正原创的地方

任何一套面向广泛领域的 schema，对某个具体领域一定不够用。经典的两条路：

- **(a) 做得宽松**（Markdown、HTML）→ 什么都能写，于是什么都校验不了、什么都处理不了
- **(b) 让人改 schema** → 工具失效、内容无法交换、升级即灾难

DITA 的答案是第三条路，也是它对信息架构领域的真正贡献：

> **任何扩展都必须声明自己的派生链，且派生链必须能在不查 schema 的情况下读出来。**

拆开看两个要求：

**要求一：声明派生链。** 每个新元素必须能一对一映射回一个已有元素。

**要求二：派生链写在数据里，不在 schema 里。** 因为接收文档的处理器**未必持有你的 schema**。把派生链放进实例，文档就变成**自描述**的。

→ `@class="- topic/li task/step "`

### 推论 7 的连锁后果

一旦接受"派生链写在实例里"，下面全是必然：

| 后果 | 为什么必然 |
|---|---|
| 处理器按 `@class` 匹配而非元素名 | 否则遇到没见过的元素就失效；按派生链匹配则自动落到基类模板 |
| **优雅降级是内建的** | 不认识 `<uicontrol>` 的处理器把它当 `<ph>` 渲染，输出仍然正确，只是丢了修饰 |
| 泛化是 `@class` 的纯函数 | 不需要查任何 schema，读属性即可还原 |
| **专门化只能收紧，不能放宽** | 若能放宽，泛化后会产出基类不允许的内容 —— 泛化就不安全了 |

**最后一条需要展开说明。**

"专门化是子集关系"常被当成一条要背的规则。它不是规则，是**定理**：

> 若要求泛化永远产出合法的基类内容，则专门化的内容模型必须是基类的子集。

这在计算机科学里有个熟悉的名字：**里氏替换原则**。专门化元素必须能在任何期待基类元素的地方替换它。

`@class` 的作用，相当于随数据一起携带的类型信息表。

这一步的实质，是把面向对象的子类型多态应用到文档模式上；并且通过把类型信息放进数据本身，解决了"接收方没有类定义"的问题。

### 推论 8：三大扩展设施是分工的必然

若 schema 是模块化组装的，那么"谁来组装"必须有个答案。而组装者**绝不能自己定义元素** —— 否则又回到了 fork 词汇表的老路。

于是三件事各归其位：

```
选用哪些模块         → 文档类型配置（产物是外壳）
新增带派生链的词汇     → 专门化
调整单个元素        → 元素类型配置（约束 / 扩展）
```

三者共享同一条不变量：**永不修改共享模块**。

这条不变量才是"升级 DITA 版本时定制不丢"的真正原因。不是因为向后兼容做得好，而是因为**你从一开始就没碰过那些文件**。

### 推论 9：一切必须晚绑定，于是产生了处理模型

若内容与语境无关、由 map 组装，那么几乎所有东西都只能在**构建时**才确定：

- 链接目标（取决于哪个 map）
- 变量文本（取决于哪个 keydef 先出现）
- 哪些内容存在（取决于 DITAVAL）
- 结构与顺序（取决于 map）
- **甚至属性的值**（级联 + 默认 + 显式）

这就产生了一个**解析顺序的依赖图**。而这个图**不是约定，是可推导的**：

> 分支过滤会克隆分支、改变 key 名 → 所以必须**先于**键空间构造
>
> key 和 conref 会带进新的元素和属性 → 所以必须**先于**属性有效值计算

[11-处理模型.md](11-处理模型.md) 里那些"必须按此顺序"的规则，都来自这个依赖图。

## 三、代价（同样是推导出来的）

只推导优点不算分析。代价同样是从公理必然产生的。

### 代价 1：源文件不再是真相 —— 这是最大的一笔

晚绑定的必然后果：**你读源文件，无法知道读者会看到什么。**

- 那段内容会不会出现？看 DITAVAL
- 那个变量是什么？看哪个 map
- 那个链接指向哪？看 key 空间
- 甚至：这里会不会**凭空多出**一段内容？看有没有别的文件 conref push 过来

最后一条尤其糟。conref push 让内容出现在输出里，而**在源码里搜不到** —— 因为它是被别处推进来的。

范式化在数据库里也有同样的性质：范式化的数据必须 join 才有意义。但散文有一个数据没有的属性——**源码的可读性对作者本人是有价值的**。数据库的范式化不伤害任何人的阅读体验，散文的范式化伤害作者的。

**这笔代价无法通过更好的工具消除，只能缓解。** 它是公理的直接后果。

### 代价 2：付出的人和受益的人不是同一批

- **作者付出**：学类型化、忌讳语境引用、标注条件、维护 key、遵守约束
- **组织受益**：维护成本下降、翻译成本下降、变体产出成本下降

**激励错配。** 这比任何技术批评都更能解释 DITA 的实际口碑——它在"自上而下推行"的组织里活得好，在"作者自主选择工具"的地方几乎必败。

一个可检验的推论：DITA 在软件工程师群体里推不动，不是因为工程师不懂结构化（他们比谁都懂），而是因为在他们的场景里**付出和收益都归自己**，且收益很小——单产品、单渠道、变化快。此时公理的收益趋近于零，而代价不变。

### 代价 3：它在优化一个特定形状的世界

DITA 的收益 ≈ `内容规模 × 变体数 × 变更频率 × 语言数`

分母是学习成本、工具链成本、晚绑定的认知负担 —— **这些几乎是固定的**。

所以当分子里任何一项趋近 1，整个投资就变负。**这不是 DITA 做得不好，是它诚实地为一类问题优化，而那类问题不是所有人的问题。**

### 代价 4：优雅降级只保证合法，不保证保义

`@class` 保证泛化后的内容**结构合法**。它**不保证语义不丢**。

`<sensor-id>TEMP-04</sensor-id>` 泛化成 `<ph>TEMP-04</ph>` 之后，"这是个传感器编号"这个信息**没了**。降级是安全的，不是无损的。

这划定了 `@class` 机制的能力边界：它解决的是**互操作**问题，不是**语义保全**问题。

## 四、哪些是必然，哪些是历史包袱

分清这两者，才知道哪些值得学、哪些只需要忍受。

### 从公理推得出来的（换我从零设计，还会这么做）

- 内容单元以**自足性**定义边界（topic）
- 结构与内容分离（map）
- 间接寻址（key）
- 正交的条件维度
- **派生链写在数据里、可不查 schema 读出**（`@class`）
- 专门化只能收紧
- 永不修改共享模块
- 由依赖关系决定的解析顺序

### 历史选择，不是必然

| 包袱 | 说明 |
|---|---|
| **XML 作为语法** | 上面所有思想都不要求 XML。同样的架构完全可以建在别的语法上 |
| **DTD 作为原始 schema 语言** | DTD 表达力不足以完整表达专门化，早期的 `.mod`/`.ent`/shell 三件套的复杂度大半来自 DTD 的局限。后来转向 RNG 是纠偏 |
| **具体的 concept/task/reference 三分** | "要有类型"是推论，"是这三种"是选择 |
| **词汇表的庞大** | 数百个元素。可争论其中有多少是必要的 |
| **conref push** | 强大，但把"读源码能知道有什么"这个性质破坏得最彻底。它是在既有架构上打的补丁，不是从公理长出来的 |

**判断方法**：一个特性如果不能从公理推出来，且它增加了"源文件不是真相"的程度，那它多半是包袱。conref push 两条都占。

## 五、为什么是文件，不是数据库

既然是范式化，为什么不直接上数据库/CMS？

因为文档有一个数据通常没有的需求：**它要比生产它的工具活得久**。

产品手册、合规文档、航空/医疗资料的生命周期以**十年**计，而软件工具的生命周期以**年**计。绑定在某个厂商的数据库里，工具死了内容就成了考古对象。

所以：**纯文本 + 开放 schema + 公开规范**。这不是技术保守，是对时间尺度的正确判断。

这也解释了 DITA 为什么是 OASIS 标准而非某公司产品，以及为什么 `@class` 必须在**实例**里——文档要能被三十年后的、完全不知道你的 schema 的处理器读懂。

**自描述性是为长期存活服务的。**

## 六、剥离 DITA 之后剩下什么

即使你永远不用 DITA，下面这些是可迁移的：

1. **复用要求身份。** 你不能复用一个没有名字的东西。任何"消除重复"的努力，第一步都是给东西起名字。

2. **可复用性的本质是自足性，不是尺寸。** 拆得小不等于能复用。判据是"脱离原语境后是否仍然正确"。

3. **约束即价值。** 一个格式的能力不只在于允许什么，更在于禁止什么。允许"如上所述"，就是允许内容被钉死在位置上。

4. **扩展机制必须让派生链可在数据里检视。** 若扩展的语义只存在于 schema/文档/口头约定里，接收方就无法安全处理它。**自描述的数据 > 需要外部知识的数据。**

5. **只收紧，才能安全降级。** 任何"子类型"设计，若允许放宽，就失去了向下兼容的可能。

6. **配置 ≠ 修改。** 想让定制在升级中存活，唯一可靠的办法是从不修改被共享的东西，只组装和配置它。

7. **晚绑定买来灵活性，卖掉可读性 —— 每次都是。** 这个权衡在配置系统、依赖注入、模板引擎、特性开关里反复出现。DITA 把它推到了极致，因此这个权衡在 DITA 上表现得格外清楚。

8. **付出者与受益者错配，则推行必败。** 这是社会技术约束，不是技术约束，但它比技术约束更常决定成败。

---

## 七、结论

> **DITA 是把"同一个事实只应存在于一处"当作公理，不做妥协地贯彻到散文上的结果。**
>
> topic、map、key、条件化、`@class`、shell、构建流水线 —— 全是推论。
>
> 而它的全部代价，也来自同一条公理：**当事实只存在于一处，任何一处就都不再是完整的真相。**
