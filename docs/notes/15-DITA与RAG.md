# 15 · DITA 与检索增强生成（RAG）

> 论证篇，与 [12](12-DITA的哲学与原理.md) 同类：**全部内容为从前序各篇已核对机制出发的分析**。这个领域没有权威文献可核对，凡是给不出机制依据的话题（嵌入模型选型、切块参数调优）本篇一概不碰。
>
> 结论先行：**DITA 对 RAG 的价值，是它三十年前为"复用"付出的成本恰好换来了 RAG 需要的东西 —— 语义边界和结构化元数据。** 反过来不成立：为了 RAG 而上 DITA，不划算（第 5 节）。

---

## 1. RAG 的内容侧难题，与 DITA 的现成答案

RAG 系统在**内容一侧**（不谈模型侧）有三个公认的难题：

| 难题 | 通用文档的困境 | DITA 的现成机制 |
|---|---|---|
| **切块**：块边界切错，检索到的就是断头内容 | 没有语义边界标记，只能按字数或标题启发式切 | **topic 就是语义完整的最小单元** |
| **检索元数据**：过滤和排序需要每块附带结构化信息 | 没有，或散落在文件名/目录名里 | `@class`、`@subjectrefs`、条件属性、prolog（第 4 节的对照表） |
| **溯源**：答案要能指回出处 | 块和源文档的对应关系在切块时就断了 | `@id` + map 路径，天然可深链 |

第一行值得单独展开。[12](12-DITA的哲学与原理.md) 推论 2 说：topic 的边界由**自足性**定义 —— 能被独立理解的最小内容块。而"能被独立理解"与"能被独立检索、单独喂给模型后仍然成立"是**同一个性质**：两者都是"脱离原语境后内容仍然正确"这一约束。这不是巧合，是同一条约束在复用和检索两个场景的表现。所以 topic 作为切块单元不是权宜的映射，是定义上的吻合。

`<shortdesc>` 是第二个现成之物：每个 topic 自带一段作者写的摘要，可直接用于检索结果展示和重排序 —— 通用文档管线里这一步要靠模型生成，还未必比作者写的准。

---

## 2. 最重要的决定：喂"解析前"还是"解析后"的内容

[07](07-程序化处理.md) 的分水岭在 RAG 场景有明确答案：**必须是解析后（preprocess 后）的内容**。三个理由，一个比一个硬：

1. **conref 未展开** —— 源文件里是引用不是内容。嵌入源文件，检索到的块里是一个空壳元素
2. **keyref 未解析** —— 变量文本还是占位符，含产品名的问句检索不到含产品名的内容
3. **条件属性未过滤** —— 这不是质量问题，是**正确性问题**：enterprise 版的内容可能被答给 basic 版用户，internal 内容可能被答给外部用户。检索器不理解 DITAVAL，源文件里所有变体的内容混在一起

由此有两条入库路线，对应 [03](03-条件化与分块.md) 的两种过滤方式：

**路线 A：按变体分库。** 每个 DITAVAL 组合各跑一次 `dita -f dita`，各建各的索引。简单可靠；代价是库的数量等于变体数，同一段共有内容在每个库里各存一份。

**路线 B：单库 + 检索时过滤。** 用 `passthrough`（[03](03-条件化与分块.md)）把条件属性保留进解析产物，入库时转为块的过滤元数据，检索时按用户的身份属性过滤。库只有一个，正交维度不会爆炸 —— 这是 [12](12-DITA的哲学与原理.md) 推论 5（变体处理必须是正交维度）在检索层的延续。代价是检索层必须正确实现属性过滤，而且**过滤错误的后果与构建时过滤错误相同**：内容给错人。

判断：变体少（≤3）用 A，变体是多维正交组合用 B。B 的过滤逻辑要按 [03](03-条件化与分块.md) 的判定规则实现（属性内部有一个值放行即放行、属性之间任一排除即排除），不要自己发明。

## 3. 块的粒度：topic 是默认值，不是教条

- **topic 过大时**（超出上下文预算）：二级切分**沿元素边界**进行 —— `<section>`、`<step>`、`<glossentry>` 的边界由 `@class` 可靠识别（[07](07-程序化处理.md) 的按 class 编程），切出来的仍是完整语义单元。这比按字数切好的地方不在省事，在**边界处不会截断句义**
- **topic 很小时**（glossentry、troubleshooting 的单条）：整块直接入库，还可以把 [01](01-核心模型.md) 的术语 keyref 关系带上
- **图结构现成**：map 层级是父子边，reltable 是相关边，keyref/conref 是引用边 —— 做图增强检索（graph RAG）时不需要重建关系，[11](11-处理模型.md) 5.7 的 `@collection-type` 语义（`family` / `sequence`）就是现成的边类型标注

## 4. 检索元数据对照表

RAG 管线常见的元数据需求，逐项对到 DITA 的来源：

| 检索侧需求 | DITA 来源 | 备注 |
|---|---|---|
| 块的类型（概念/操作/参数） | `@class` 的最特化 token | [07](07-程序化处理.md) 的 `topic_type()` 一行代码；"how do I"类问句优先检索 task 是可实现的 |
| 主题分面 | `@subjectrefs` + subjectScheme 树 | [14](14-元数据与分类策略.md)；树给出层级检索（查"linux"命中"ubuntu"的块 —— 沿层级向上查找的检索版） |
| 受众 / 平台 / 产品 | 条件属性（passthrough 保留） | 第 2 节路线 B |
| 摘要 | `<shortdesc>` | 作者写的，不用生成 |
| 时效 | `<critdates>` | **仅当按 [14](14-元数据与分类策略.md) 第 5 节由系统注入才可信** —— 手填的日期喂给"优先新内容"的排序器是毒药 |
| 溯源深链 | `@id` + map 路径 | `@id` 稳定性因此再加一分（[08](08-实践建议.md)：发布后不改） |
| 语言 | `@xml:lang` | [13](13-翻译与本地化.md)；多语言库的过滤维度 |

这张表的前提与 [14](14-元数据与分类策略.md) 第 6 节相同：元数据的维护流程真的在跑。失真的元数据喂给检索器比没有更糟 —— 检索器会**自信地**用错误的元数据过滤和排序。

## 5. 反面：DITA 帮不上和添乱的地方

诚实清单，与前面同等重要：

1. **解析摧毁复用标识。** conref 展开后，同一片段的内容在解析产物里是普通文本 —— 路线 A 的多个库里它各存一份，向量重复、更新时要全部重嵌。解析产物默认**不携带**"这段来自哪个源片段"的标记，想要就得构建侧自己注入（这属于实现层工作，规范不管）。复用省下的翻译成本（[13](13-翻译与本地化.md)），在嵌入成本上并没有对应的节省
2. **结构化内容的嵌入效果是通用难题。** 表格、语法图、步骤序列的向量表示质量差，DITA 的精细标记在这里帮不上 —— 它能做的只是让你**识别**这些块（按 `@class`）并单独处理
3. **投入判断不因 RAG 改变。** [12](12-DITA的哲学与原理.md) 代价 3 的公式照常成立：内容本来就在 DITA 里，RAG 收益是白拿的；内容不在，"为了 RAG 做结构化迁移"的成本远超过收益 —— 通用切块管线虽然糙，但便宜得多。**RAG 是已用 DITA 的组织的新分红，不是上 DITA 的新理由**

---

## 6. 结论

把本篇压缩成一句话：

> RAG 需要"语义完整的块 + 可信的结构化元数据"，而这两样东西恰好是 DITA 为复用与多变体付出三十年成本换来的副产品。已经在 DITA 里的内容，做 RAG 时切块、元数据、溯源、图结构全部现成；不在的，别为此而来。

关键的工程决定只有一个（第 2 节）：**用解析后的内容，并想清楚条件过滤发生在入库前还是检索时。**
