# 11 · 处理模型

> 规范定义的**处理期望**，不是 DITA-OT 的实现。[04](04-工具链与构建.md) 讲的 preprocess 流水线是某个实现怎么做；这一篇讲规范要求怎么做。
>
> **自研处理逻辑若不遵循本篇的规则，结果会与 DITA-OT 不一致，且不符合规范。**

规范 "DITA processing" 章节的完整子树：导航 / 索引 / conref / 条件处理 / **元数据级联** / 分块 / **分支过滤** / **排序** / **确定属性有效值**。

---

## 1. 确定属性的有效值

这是整个处理模型里最该先掌握的一条 —— 它决定了任何一个属性最终"到底是什么值"。

### 五级优先级

> 有效值按此顺序解析，**且在 `@conref` 与 `@keyref` 解析之后**：

```
1. 显式指定的值（explicit value）
2. XML 语法的默认值或固定值（grammar default / fixed）
3. 级联值（cascading value）
4. 受控值默认（controlled-value default）
5. 处理器提供的默认（processing-supplied default）
```

### 每一级的含义

| 级别 | 来源 | 例子 |
|---|---|---|
| 1 显式值 | 作者在该元素上写的 | `<p platform="linux">` |
| 2 语法默认/固定 | **doctype shell 配置的默认属性** | `@class`、`@specializations` |
| 3 级联值 | 从 map 祖先级联下来的 | map 上设的 `@audience` |
| 4 受控值默认 | subjectScheme 的 `<defaultSubject>` | 未指定 `@platform` 时的默认平台 |
| 5 处理器默认 | 实现自行决定 | `@toc` 未指定时按 `yes` |

### 三条推论

**推论一：`@class` 来自第 2 级。** 这再次印证了 [09](09-架构基础.md) 里 shell 的作用 —— 不走 schema 就没有第 2 级，`@class` 自然是 `None`。

**推论二：解析顺序不能颠倒。** 必须先解析 conref 和 keyref，**再**求属性有效值。因为 conref 会把别处的元素及其属性拉进来，keyref 会带来 map 上的属性 —— 这两步之前算出的"有效值"是错的。

**推论三：级联值排在显式值之后。** 元素上自己写了什么，永远压过从 map 级联下来的。

### 多值属性

> 对于多值属性，加性与非加性行为遵循 `@cascade` 的规则。

见下一节。

## 2. 元数据级联

### 定义

> 元数据级联是**为一个 map 或一个 topicref 指定的元数据元素和属性，向下级联到嵌套引用**的过程。

关键限定：**级联作用于包含层级（containment hierarchy），不是专门化层级。** 也就是说它沿 map 的树形结构往下走，和元素的 `@class` 派生链无关。

### 会级联的属性（完整清单）

```
@rev
@props 及其全部专门化：@audience  @deliveryTarget  @platform  @product  @otherprops
@linking   @toc   @search
@format    @scope  @type
@xml:lang  @dir    @translate
@processing-role
@cascade
@subjectrefs
```

**记这份清单是有实际价值的** —— 不在表里的属性不会级联。"我在 map 上设了 X 为什么 topic 里没生效"，第一步就是查它在不在这张表里。

注意 `@cascade` **自己也会级联**。

### 加性 vs 非加性

| 情况 | 行为 |
|---|---|
| **多值属性** | **加性** —— 祖先与后代的值**合并**（除非 `cascade="nomerge"`） |
| **单值属性** | **最近祖先胜** —— 取距离最近的那个已指定值 |

举例（多值、加性）：

```xml
<map audience="admin">
  <topicref href="a.dita" audience="developer"/>
</map>
```

`a.dita` 的有效 `@audience` 是 **`admin developer`**，不是 `developer`。

这一点极易踩坑：**你以为在子节点上"覆盖"了，实际是"追加"了。** 于是本该只给 developer 看的内容，因为继承了 `admin` 而在 admin 版本里也出现了。

### `@cascade`

两个取值：

| 值 | 语义 |
|---|---|
| **`merge`**（默认） | 加性合并，祖先的值与后代的值并集 |
| **`nomerge`** | **停止加性合并** —— 后代不再累积祖先的值 |

> 重要限定：`nomerge` **并不完全关闭级联**，它阻止的是**累积**，不是全部继承。

所以上面的例子改成：

```xml
<map audience="admin" cascade="nomerge">
  <topicref href="a.dita" audience="developer"/>
</map>
```

`a.dita` 的有效 `@audience` 就是 `developer`。

**实践建议**：多产品线/多受众的大型 map，**在根上显式写 `cascade="nomerge"`**，让子节点的条件属性表现得符合"覆盖"直觉。默认的 merge 行为在深层嵌套时会累积出难以预料的组合。

### 关系表里的级联

reltable 的层级和普通包含层级不同，级联路径是：

```
<reltable> → <relcolspec> → <relrow> → <relcell> → <topicref>
```

在 `<relcolspec>` 上设 `@type` 或条件属性，会级联到该列所有单元格里的 topicref。这是给整列统一打标的正确位置。

## 3. conref 解析时的属性规则

内容被拉过来时，最终元素的属性从**引用方**和**被引用方**两边合成。优先级：

```
1. 引用方（referencing element）上指定的全部属性
   —— 但值为 "-dita-use-conref-target" 的除外
2. 被引用方（referenced element）上指定的全部属性
   —— 但 @id 除外
```

**核心结论：引用方赢，`@id` 永远不跟着走。**

`@id` 被排除是必然的 —— 否则一次 conref 就会把目标的 id 复制过来，同一文档里出现重复 id。

另外两条容易想当然的规则：

- **属性值从不合并。** 即使是 `@audience` 这类多值属性，最终值也是**整体取一边**（引用方或被引用方），不做并集。注意这与元数据级联的"加性合并"（第 2 节）行为相反 —— 级联会合并，conref 合成不会
- **`@xml:lang` 有特殊处理**，不完全走上面的两级规则（语言标注需要保持内容与语言的一致性）

### `-dita-use-conref-target`

一个规范定义的特殊值，用来解决**必填属性**与 conref 的冲突。

场景：某元素有个必填属性，但你想让它的值也从 conref 目标那里来。直接不写属性会校验失败，写了又会覆盖目标的值。这时写：

```xml
<someElement requiredAttr="-dita-use-conref-target" conref="..."/>
```

语义：**"这个属性别用我的，用目标的。"**

规则细节：

- 只有当**被引用方**也把该属性写成 `-dita-use-conref-target`，**且引用方要么没写该属性、要么也写成这个值**时，解析后的元素才会保留这个值
- 如果整条 conref 链解析完，最终元素上还有属性是这个值，**必须视同该属性未指定**

### 与第 1 节的关系

conref 的属性合成发生在**属性有效值求解之前**（第 1 节说了：有效值在 conref/keyref 解析之后才算）。顺序是：

```
conref/keyref 解析（含属性合成）→ 求属性有效值（五级优先级）
```

## 4. 排序

### `<sort-as>`

每个可排序元素有一个**基础排序短语（base sort phrase）** —— 通常是 `<title>` 的内容；无标题元素则由属性值生成或构造。

`<sort-as>` 的作用是修改它：

> 处理器**必须**通过把 `<sort-as>` 的内容**前置（prepend）**到基础排序短语上，来构造**有效排序短语**。

规范给的例子：标题为 "24 Hour Support Hotline" 的 topic，加上 `<sort-as>twenty-four hour</sort-as>`，有效排序短语是：

```
twenty-four hour24 Hour Support Hotline
```

注意是**拼接**，不是替换 —— 这个细节容易想当然。

### 排序规则（collation）留给实现

> 规范**不定义**排序规则与区域设置。"排序与分组的细节是实现相关的。处理器可能提供不同的机制来定义或配置排序规则与分组细节。"

处理器**应当**显式文档化它如何确定基础排序短语。

**后果：同样的标记，不同处理器可能排出不同顺序。** 这是规范允许的，不是 bug。

### 中文场景

对需要**注音排序键**的语言（中文、日文），`<sort-as>` 就是那个机制 —— 作者**手工**提供拼音或假名：

```xml
<topic id="zhang">
  <title>张三</title>
  <prolog>
    <sort-as>zhangsan</sort-as>
  </prolog>
  ...
</topic>
```

**但 DITA 本身不自动化这件事。** 拼音要人写或工具生成。

**给中文内容的实际建议**：

1. 索引和术语表**必须**规划 `<sort-as>` 策略，否则排序结果由处理器的默认 collation 决定，通常不是你要的
2. 拼音可以用工具批量生成，但**多音字必须人工复核**（"重庆" "长沙" "厦门"）
3. 如果要按笔画排序，同样走 `<sort-as>`，自己构造排序键
4. **在选型阶段就测试你的处理器的中文 collation 行为** —— 这是规范不管的地方

## 5. 导航：目录（TOC）的生成规则

默认规则：**map 里每个引用了 topic 或指定了导航标题的 `<topicref>`，生成一个 TOC 节点**。四种例外不生成：

1. `@processing-role="resource-only"`（`<keydef>` 不进目录的原因就在这）
2. 被条件处理过滤掉
3. 既没有引用资源、也没有导航标题
4. `<topicgroup>` —— **即使给它写了导航标题也不生成**（这是它与 `<topichead>` 的处理级差异：`<topichead>` 靠导航标题生成节点）

另外两条：

- **`@toc` 会级联**：`toc="no"` 使整个子树退出目录，除非某个后代显式写回 `toc="yes"`（与 [第 2 节](#2-元数据级联)的级联清单一致 —— `@toc` 在表里）
- **map 引 map 时，被引 map 的导航树在引用点并入**引用方的导航树 —— 多 map 拼一本书的处理依据

节点的显示文本取**有效导航标题**，其确定规则见 [01](01-核心模型.md) 的 `<titlealt>` 合并规则（topicref 优先于 topic 内）。

> 2.0 规范的"导航"一节只覆盖**目录**与**替代标题**两个子页；链接生成的规范内容在语言参考的属性与 reltable 页面，见下文 5.7。

## 5.5 索引

规范定义的索引设施（生成与否、怎么渲染由实现决定）：

| 设施 | 语义 |
|---|---|
| `<indexterm>` | 索引项。可出现在 **topic 的 prolog**、**正文任意处**、**map 的 topicmeta** 三类位置 |
| 嵌套 `<indexterm>` | 多级索引 —— 内层是外层的次级条目（secondary / tertiary） |
| `@start` / `@end` | 成对使用，把一段**跨度**（而非一个点）标为索引范围，适合覆盖一段长讨论 |
| `<index-see>` | "见 X" —— 重定向到另一个索引项 |
| `<index-see-also>` | "另见 X" —— 补充参照 |
| `<sort-as>` | 与 indexterm 配合指定排序短语（第 4 节的规则同样适用 —— 中文索引必须规划它） |

实践要点：

- **放 prolog 还是放正文**：prolog 里的 indexterm 指向整个 topic；正文里的指向具体位置。打印/PDF 场景两者有页码差异，在线场景通常都落到 topic
- map 的 topicmeta 里也能打索引项 —— 与元数据级联同理，适合在不改 topic 的前提下给一批内容补索引
- 处理器"可以"生成索引 —— 是否生成、如何渲染是实现决定；`-f html5` 默认不出独立索引页，PDF 走 `<indexlist>`（bookmap 的 backmatter，见 [01](01-核心模型.md)）

## 5.7 链接生成：`@collection-type` 与 reltable

### `@collection-type`：声明子节点之间的关系

设在 `<topicref>`（或 `<relcell>`）上，说明其子 topic 彼此如何相关，处理器据此生成链接：

| 值 | 语义 |
|---|---|
| `unordered` | 子 topic 的顺序无意义 |
| `sequence` | **顺序有意义** —— 处理器通常在子 topic 之间按序生成前后链接 |
| `choice` | 子项中应**选择其一** |
| `family` | **紧密分组** —— 子 topic 不仅与当前 topic 相关，**彼此之间也互相关联**（即互链） |

### `@linking`：控制参与链接的方向

| 值 | 语义 |
|---|---|
| `normal` | 可链出也可被链入；用于**覆盖上层设置** |
| `sourceonly` | 只能链出，不能被链入 |
| `targetonly` | 只能被链入，不能链出 |
| `none` | 不参与链接生成 |

两个属性都在第 2 节的级联清单里 —— 在 `<relcolspec>` 上设一次，经"列 → 行 → 单元格 → topicref"的路径整列生效。

### reltable 的链接规则

补全 [01](01-核心模型.md) 里只说了"自动互链"的部分：

- **同一行、不同单元格**的 topic 之间生成链接；**同一单元格内默认不互链**
- 同格的 topic 确实相关时，在 `<relcell>` 上设 `collection-type="family"`
- 某列只作为"被参考资料"、不需要回链的：在 `<relcell>` 或 `<relcolspec>` 上设 `linking="targetonly"`
- reltable 的 `@toc` 默认为 `no` —— 关系表天生不进目录

### 层级链接是实现惯例

map 层级本身产生的父/子/兄弟链接（DITA-OT 的 maplink 步骤），规范**没有单列生成算法** —— 上面两个属性给出的是语义约定，具体生成哪些链接、渲染成什么由处理器决定。跨处理器迁移时这部分行为要实测。

## 6. 给程序化处理的检查清单

自研处理逻辑时，按这个顺序做才与规范一致：

```
1. 分支过滤求值 + map 层的条件过滤    ← 必须最先，两者都会改变键空间
2. 构造键空间
3. 解析 keyref / conkeyref
4. 解析 conref（含属性合成：引用方优先，@id 除外）
5. 求属性有效值（五级优先级，含级联）
6. topic 内容的条件过滤
7. 其余处理
```

### 为什么条件过滤要拆成两步

**map 层的过滤必须先于键空间构造。** 一个 `<keydef>` 若被 DITAVAL 排除，它就不该进入键空间 —— 这正是 [02](02-复用.md) 里"用条件化去掉一个 keydef，让某个变体走不同的 key 定义"这一用法成立的前提。分支过滤先于键空间的规范约束（见 [10](10-寻址与键空间.md)）是同一逻辑的显式版本。

**topic 内容的过滤可以晚。** 过滤 topic 里的一个 `<p>` 不影响键空间，放在引用解析之后做是安全的。

这里有一个真实的依赖环需要意识到：过滤判定用的是**属性的有效值**（含从 map 级联下来的值），而完整的五级有效值求解又排在 conref/keyref 解析之后。实现上的解法（DITA-OT 即如此）是分两次：先用 map 级联后的属性做过滤（第 1 步），引用全部解析后再做完整求值与内容过滤（第 5、6 步）。规范只显式约束了两端 —— 分支过滤先于键空间、有效值后于 conref/keyref —— 中间怎么排是实现的自由，但违反这两端就一定错。

**最容易错的三处**：

1. 把分支过滤或 map 层过滤放在建键空间之后 → key 全错
2. 在 conref 解析前就算属性有效值 → 拉进来的内容属性不对
3. 忘了多值属性默认是**加性**级联 → 条件化在深层嵌套时静默出错
