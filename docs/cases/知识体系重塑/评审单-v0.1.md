## G. 对标治理机制 ⚡（防"五年后又成黑洞"）

内容层已有 volatility 防内容腐烂；分类树本身也会过时，需对称的机制防**结构**腐烂。已写入词表的 `benchmark-registry`：九分支各登记对标锚点 + 上次核对日期 + 复核档位 + 事件触发条件。

**设计原则（灵活优先，不是定期作业）：**

| 原则 | 内容 | 裁定 |
|---|---|---|
| 事件触发为主 | 某分支连续 ≥3 篇笔记无处安放、或外部锚点大改版 → 触发对标。这是"按需"的核心 | |
| 日历到期只兜底 | 过期仅由工具 flag 提示，**不阻塞**任何写作/构建（软提示非硬门） | |
| 到期默认轻量 | 几分钟确认锚点有无大变即可续期；只有发现大变或事件触发才跑全量五路对标 | |

**复核档位（cadence，可逐分支调）：**

| 档位 | 分支 | 默认周期 | 裁定 |
|---|---|---|---|
| volatile | ai | 半年 | |
| annual | security / engineering / web / data | 一年 | |
| stable-on-trigger | network / foundations / content-engineering | 靠事件触发，无固定周期 | |
| on-trigger | lang | 纯事件触发 | |

**开放问：** 到期提示希望怎么收到？（建议：不做自动化，复核纪律作为一条 checklist 项，在每次大批量重写前顺手扫一遍 registry 的日期——最轻、不引入工具依赖。也可留到工具链阶段再定。）
