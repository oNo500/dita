# 两个架构角色的分工（速查）

> 你一个人分饰两角（[00](../../notes/00-角色与边界.md)：小团队里信息架构师与 DITA 架构师常由同一人担任）。这份文档的用处不是把活分给两个人，而是让你**切换帽子时知道现在戴的是哪顶**——避免"以架构师身份造零件时顺手改了分类"这种越界。

## 一句话区分

| 角色 | 管什么 | 记法 |
|---|---|---|
| **信息架构师**（information architect） | 内容**怎么组织** | 放哪、怎么分类、怎么连 |
| **DITA 架构师**（DITA architect） | 内容**用什么语法结构** | 能写什么元素、什么属性、什么规则 |

信息架构师偏**内容**，DITA 架构师偏**语法（schema）**。前者的产物是"分类和地图"，后者的产物是"文件格式的定义"。

## 产出物对照（来自 00）

| 信息架构师 | DITA 架构师 |
|---|---|
| root map（内容的总组织） | 文档类型外壳 shell（装配 schema） |
| subject scheme 受控词表 | 词汇模块 / 专门化（造新元素、新属性） |
| 新文档类型的**规划**（要哪些类型） | 约束模块 / 扩展模块（改元素的规则） |

注意最后一行的交接：**信息架构师规划"要哪些类型"，DITA 架构师实现"那些类型的语法"**。一个提需求，一个造实现。

## "这件事归谁"判断表

| 要做的事 | 归谁 |
|---|---|
| 加一个新主题分类（如 `vector-search`） | 信息架构师 |
| 把一批 topic 组织进 map | 信息架构师 |
| 定 subjectScheme 词表、受控值 | 信息架构师 |
| 决定某内容标什么成熟度/时效 | 信息架构师（用值，不造属性） |
| 写 root map、领域 map、交付物 map | 信息架构师 |
| 造一个新属性 `@props/maturity`（RNG 属性域模块） | DITA 架构师 |
| 写文档类型外壳 shell | DITA 架构师 |
| 写约束模块（强制 shortdesc、禁 draft-comment） | DITA 架构师 |
| 决定用 concept 还是新造 `<rule>` 专门化 | DITA 架构师 |
| 写 Schematron 业务规则 | DITA 架构师 |
| 定"要不要 rule 这个类型" | 信息架构师提，DITA 架构师实现 |

## 最容易混的一处：属性专门化

加一个条件维度 `@props/maturity`，两个角色各做一半（[00 §7](../../notes/00-角色与边界.md)：造零件 vs 选零件）：

- **DITA 架构师造零件**：从 `@props` 派生出 `@maturity` 属性，写 RNG 属性域模块 —— "这个属性存在了"
- **信息架构师定值集**：`draft / curated / verified`，在 subjectScheme 里绑定 —— "这个属性能取哪些值"

零件由架构师造、值域由信息架构师定，两者在 `<enumerationdef>` 处交接。这就是为什么词表（信息架构师）和 shell（DITA 架构师）是两个文件、两双手。

## 一条不能越的界（DITA 架构师内部）

DITA 架构师自己还有一条铁律（[00 §7](../../notes/00-角色与边界.md)）：**外壳 shell 不得自己声明任何元素**——只能装配模块、配默认值。造元素是"词汇模块"的活，选元素是"外壳"的活，同一个角色也要分开做，混在一起等于分叉了词汇表。

## 这次实践中各自实际交付了什么

| 信息架构师（已交付） | DITA 架构师 |
|---|---|
| subjectScheme.ditamap v0.2 ✅ | 类型映射（规划）✅ |
| 主题树九分支 + 对标 ✅ | 三个属性专门化（规划，值集已绑）⚠️ RNG 未写 |
| 三属性值集 + 治理登记 ✅ | shell 装配清单（规划）⚠️ RNG 未写 |
| root/领域 map（规划）⚠️ 实体待 Phase 2 | 约束模块 + Schematron（规划）⚠️ 未写 |

**当前状态一句话**：信息架构师的核心产出（词表）已是实体文件；DITA 架构师的产出还停在规划，"造零件"（RNG/约束/Schematron）待 Phase 2 建库时实现。

## 维护治理归谁：角色不止建设期

上面讲的是建设期分工（造什么零件）。但角色职责不止建库那一刻——体系建成后会腐烂，需要有人持续维护，这也要分清归谁。

| 维护职责 | 归谁 | 机制 |
|---|---|---|
| 分类树对标（防结构停滞、跟上业界） | 信息架构师 | 词表内 benchmark-registry：事件触发为主、到期兜底 |
| 成熟度/时效复核（防内容过时） | 信息架构师 | maturity/volatility 标注 + verified 日期戳 |
| 语法演进（DITA 版本升级、shell 跟进） | DITA 架构师 | 锁定版本、从稳定基类派生 |

因果要理顺：**若没人负责维护治理，分类架构就停滞、跟不上业界，内容也跟着落后**——这正是旧库从体系退化成黑洞的机制。维护治理不是可选项，是防腐烂的必需。
