# 架构与边界

> 三层各自做什么、不做什么，以及规则归谁实现。写于 2026-08-15，起因是 `kb` 与 `dita-tools` 各自演进出现割裂。
>
> **本轮只画边界，不定工具终态**——规则归属表里标"待定"的项，是真的还没决定，不是忘了填。

## 一、为什么需要这份文档

三块本来在不同仓库，合并后没人定过它们的关系，于是出现四个接缝：

1. **没有根。** 仓库根目录只有三个文件夹，没有入口文档。三份 README 各说各的，只有 `dita-tools/README.md` 提了一句"作为 kb 的配套工具链"。（已补：根 [README.md](../README.md)）
2. **同一条规则被两份规划各自认领。** `ia-governance.md`（现存 `research/cases/kb-redesign/`）说 R11 加进 `check-rules.xsl`；`dita-tools` 的架构计划说 R11 进 `dita_validate`。两边都动，就会长出两个都不完整、还得互相同步的实现。
3. **唯一事实源没被当成唯一事实源。** `vocab/subjectScheme.ditamap` 定义了 51 个 `dim-*` 与三个属性值集，但 `check-rules.xsl` 里是**手抄的副本**。改词表不会让校验跟着变。
4. **工具够不着内容。** `dita-tools` 有 map 解析器，没有 topic 解析器；`TopicMeta` 类型定义了却没有生产者。它因此读不到任何 `@props` 专门化属性，接不上覆盖度与业务规则。

## 二、三层契约

```
research/    研究与设计   产出：判据、规则规格、裁定记录
  │                        （原名 docs/，2026-08-15 更名——仓库级文档另立 docs/）
  │                        不做：不实现、不校验
  ↓ 规格（R1–R11 的定义与理由）
kb/          内容正本     产出：内容 topic、受控词表（唯一事实源）、交付物
  │                        不做：不定义规则的"为什么"（那在 docs）
  ↓ 值集与内容（subjectScheme + topics/ + maps/）
dita-tools/  执行引擎     产出：校验结果、IA 视图
                           不做：不自带值集、不重新定义规则语义
```

**依赖单向，反向即违规。** 三条具体的红线：

- 工具**不得**内联合法值清单——一律从 `subjectScheme.ditamap` 读。当前 `check-rules.xsl` 的硬编码副本是违规的历史欠账，谁接手 R11 谁一并还。
- 规则的理由写在 `research/`，实现里只留一行指向规格的引用。工具的 README 不承载"为什么这么定"。
- `kb` 的**内容与发布**不依赖 `dita-tools`：一切 `.dita`/`.ditamap` 是合法 DITA，DITA-OT 足以校验与构建，内容永不被自研工具绑架。**治理自动化归平台**（2026-08-15 随终态落定修订——原表述"现有脚本仍能跑完整条链"在脚本逐个退役后不再成立，但精神不变：丢了 dita-tools，丢的是治理便利，不是内容）。

## 四、两个治理主体：库的形状 vs 每一篇

R11 的归属之所以两份规划都伸手认领，根子在这条线一直没画：

| | 管什么 | 谁执行 | 判据来源 |
|---|---|---|---|
| **IA 治理** | 库的**形状**：分支建了没、内容挂上没、分类树该不该重新对标 | `dita-tools ia` | `subjectScheme` + map 结构 |
| **内容规则治理** | **每一篇**合不合规：shortdesc、来源、术语、属性值 | `review.sh`（R1–R11） | `rules.sch` |

`@dimension` 值合法性横跨两边——它既是单篇的属性合规（R11），又是分类体系的使用情况（哪些维度从没被用过）。**横跨不等于要实现两遍**：值集只有一个来源（`subjectScheme`），谁实现都从那里读，两边看的是同一份判定的不同切面。

### IA 治理需要三样东西

治理不是查看。要判断而不只是描述，得同时有现状、应然、时间：

| 面 | 回答 | 数据来自 | 现状 |
|---|---|---|---|
| **现状** | 实际长什么样 | `maps/` + `topics/` | ✅ 树、分支统计、孤儿、非法值 |
| **应然** | 本该长什么样 | `subjectScheme` 主题树（81 个规划节点）；全景的 `planned-dimension` | 维度那半已做，主题树那半未做 |
| **时间** | 什么时候开始烂 | `benchmark-registry`（对标锚点 + 上次日期 + 复核档位） | 未做 |

没有「应然」，工具只能说"这里 3 篇、那里是空的"；有了它才能说"这个分支规划了 18 个子主题、建了 0 个"。没有「时间」，看不见分类树自身的腐烂——而词表里那 10 条对标登记，写的正是"这棵树多久该重新对标一次"。

**所以 `subjectScheme` 不是另一个视角，它是让 `ia` 从查看器变成治理工具的那块拼图。** 它不该有独立的子命令：按数据来源切是工具的切法，按概念切，它们是同一件事的三面。

### 工具生态终态（2026-08-15 已决，即原待定项 1）

**dita-tools 是唯一工具平台**，DITA-OT 是它踩着的发布黑盒；`kb/scripts` 里的脚本是**待吸收的临时能力载体**，不是要安置的家当。能力地图：

| 能力 | 今天 | 收敛到 |
|---|---|---|
| 结构校验（RNG）/ 发布 | DITA-OT | 留 DITA-OT，不自造 |
| 业务规则 lint（R1–R11） | `check-rules.xsl` + `ia` 各持一段 | `dita-tools lint` |
| 术语扫描（R7） | `term-normalize.py` | `dita-tools lint` |
| 维度覆盖 | `dimension-coverage.py` | `dita-tools ia`——已实现，**可第一个退役** |
| IA 治理骨架 | `dita-tools ia` | ✅ 已在 |
| 链接活性 | `link-check.py` | `dita-tools links` |
| 交付物构建编排 | `build-agent-rules.sh` | `dita-tools build`（包 DITA-OT） |
| 预览 / 页面渲染 | `preview.sh`（批处理） | `dita-tools preview`——本就在其立项理由里 |

**吸收纪律**：能力成熟一个、退役一个脚本，每项能力只迁移一次；**不建 `tools/` 伞目录**——那是给注定消失的东西修候车室。`kb/` 的「纯声明性」不变式（目录里只有 XML/RNG/DITAVAL，无一行可执行代码）是吸收完成后的终态，届时 kb 这个名字与内容完全相符。过渡期的统一入口由根 `Justfile` 承担，使用者无需知道哪条命令是脚本、哪条是平台。

## 六、参照实现只能借机制，不能借需求

2026-08-15 的实例，值得当成一条纪律记着。

`dita-tools` 的架构计划里，立项的头号理由是「看不到……**哪些域是空的**」，而三百行之后的实现规格写的是「XML → AST（**递归展开 mapref**）」，参照 DITA-OT 的 `MaprefModule.java`。展开即内联，**空 map 会连同标题一起消失**——这份计划的实现规格，恰好取消了它自己的头号需求。代码忠实执行了规格，测试也照着规格写（`expands_mapref_inline` 直接给缺陷背书），于是测试全绿、缺陷存活，直到工具第一次真跑在 kb 上才暴露。

DITA-OT 那样做没有错：它要产出页面，空 map 本就没有页面可产。**错在借的时候只问了"它怎么做"，没问"它为什么这么做、我的目的和它一样吗"。**

由此定三条：

- 参照实现给的是**机制**。机制背后的目的必须重新对照本项目的立项理由，不一致就不能照抄。
- 每条实现规格要能指回它服务的哪条需求；指不回去的规格，要么是多余的，要么是抄来的。
- **测试照规格写，所以测试兜不住规格本身的错。** 规格与需求的一致性只能靠人对照，或者靠让工具尽早跑在真实数据上——这也是"工具先行、小步验证"的实际理由。

## 七、文档纪律

- `research/cases/` 下的评审单、阶段总结、Phase 结论是**历史记录**：按当时原样保留，不翻新路径、不追改结论。要更正就新写一篇并注明取代关系。
- 现行文档（各级 README、设计正本、进行中的计划）**必须与现实一致**，发现不符即改。
- **文件命名（2026-08-15 定）：全库 ASCII kebab-case。** 例外仅三类，都是外部惯例优先：
  ① 众所周知的大写文件（README / LICENSE）；② DITA/RNG 制品沿用 DITA 元素命名
  （`subjectScheme.ditamap`、`*AttDomain.rng`）；③ Rust 沿用 crate 蛇形命名。
  设计/计划类文档加日期前缀（`2026-08-15-skeleton-design.md`）。中文只出现在内容里，不出现在路径里。
  历史档（`research/cases/`）的**文件名**已随规约迁移（导航元数据，非内容），**正文仍不翻新**。
- 判断与事实分档写：来源节区分「已核对」与「判断与通用实践」，见 `kb/topics/writing/writing-sourcing.dita`。

## 九、执行顺序（已定）

**工具先行**：先把治理链打通，再批量扩内容。理由是现在只有 22 篇，规则和标注方式都还改得动；等写到两百篇再改工具，返工成本按篇数放大。

**工具这一侧，当前主线是 IA 治理**（2026-08-15 定，三面见 §四），不是预处理引擎。IA 视角有两个用途，前者是现在的迫切需求：

1. **建库之初的全局观测与设计** —— 知识树长什么样、哪些域是空的、哪些域缺哪一类内容、哪些还是 draft、哪些维度没覆盖。这是决定"下一批写什么"的依据。
2. **面向使用者 / 作者视角的页面渲染**（未来）—— 从"结构观测"走向"内容可读"。

**`topic` 解析器因此归位为 IA 视角的前置，不是与之并列的另一条赛道**：上面第 1 条里除"知识树"和"空领域"外的每一项，都要求读到 topic 的 `@dimension` / `@maturity` / `@volatility` 与类型。R11 是它到位后的顺带产物。Key Space / Conref 等预处理大件顺延。

前置条件已解除：`build-essential` 已装，`dita-tools` 于 2026-08-15 首次编译通过、测试全过。
